# Releasing tui

GitHub Releases are the canonical release history for tui. Release notes should
explain the user impact first and retain the generated pull request list for
traceability.

## Before a release

1. Choose the next version using semantic versioning.
2. Apply one release-note label to every pull request included in the release:
   `enhancement`, `bug`, `documentation`, `dependencies`, or `github_actions`.
   The release-note label workflow derives the label from the pull request's
   Conventional Commit prefix. Confirm it before merging. Pull requests
   without one of these labels appear under **Maintenance**.
3. Update the version in `package.json` and any version references in the
   documentation.
4. Run `pnpm test`, `pnpm test:coverage`, and `pnpm typecheck`.
5. Merge the version change into `main`. After CI succeeds, the tag and release
   workflows create the version tag, Docker image, and draft GitHub Release.
6. Edit the draft using the structure below, verify its tag and full changelog
   range, and publish it when it is ready to announce.

## Release note structure

Edit the generated GitHub Release notes so they use the following order. Omit
empty sections, except that `Breaking changes: None.` can be useful for minor
and major releases.

```md
# tui vX.Y.Z

A one- or two-sentence summary of the release and why users should upgrade.

## Highlights

- Describe the most important user-visible improvement.
- Keep this list short and outcome-focused.

## New features

- Describe a user-visible feature ([#123](pull-request-url)).

## Fixes

- Describe the corrected behaviour ([#124](pull-request-url)).

## Breaking changes

None.

## Upgrade

Describe required configuration changes or migrations. Omit this section when
no special action is required.

## Known issues

- Describe a known limitation and its workaround.

## Generated changelog

Keep the categorized pull request list generated by GitHub here.

**Full changelog:** [vPREVIOUS...vX.Y.Z](comparison-url)
```

Write summaries for users rather than copying commit subjects. Dependency,
test, refactoring, CI, and documentation work should remain in the generated
changelog unless it materially changes installation, configuration, or usage.

## Versioning guidance

- **Patch** releases contain backwards-compatible fixes and maintenance.
- **Minor** releases add backwards-compatible functionality. Before v1.0.0,
  call out any breaking change prominently even when it is shipped as a minor
  version.
- **Major** releases may contain breaking changes and must include migration
  instructions.

Do not publish a release with only the generated pull request list. Add the
summary, highlights, breaking-change status, and any required upgrade steps
before publishing it.
